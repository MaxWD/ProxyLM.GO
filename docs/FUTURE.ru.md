## 1. Persistence статистики perf (приоритет: высокий)

**Проблема:** `PerfTracker` хранит все наблюдения `(server, model, endpoint)` в RAM. При рестарте daemon'а история обнуляется; регрессия начинается с нуля — первые 2–3 запроса не дают метрик.

**Решение:** сохранять `[]perfObservation` в SQLite (новая таблица `perf_observations`), грузить при старте. Ограничить размер хранения (например, 1000 наблюдений на ключ, FIFO).

**Риски:** небольшой overhead на каждый завершённый запрос; требуется миграция 0003.

---

## 2. Persistence in-memory очереди (приоритет: средний)

**Проблема:** при рестарте daemon'а все запросы из `pending` теряются — клиенты получают connection error и должны повторять сами. В production-инсталляциях это может вызывать значимые потери.

**Решение:** при старте с флагом `--durable-queue` сохранять `pending` в SQLite и восстанавливать при следующем старте. Запросы в статусе `running` при восстановлении переводятся в `queued` (повтор). Реализация требует гарантии идемпотентности на стороне клиента или явного флага `client_supports_retry`.

**Ограничение:** persistence очереди намеренно отложена до v0.2+ (U-3 в SRS.md).

---

## 3. Web UI (приоритет: низкий)

**Проблема:** TUI требует терминала; при удалённом мониторинге через браузер TUI неудобен.

**Решение:** минималистичный Web UI на том же WebSocket (`/admin/stream`), без зависимостей на фронтенде (vanilla JS + EventSource или WebSocket). Табличный вид запросов и шапка серверов — аналог TUI.

**Ограничение:** явно в out-of-scope MVP (SRS §8).

---

## 4. Аутентифицированный WS-мультиплекс с фильтрацией событий (приоритет: средний)

**Проблема:** текущий `/admin/stream` отдаёт все события всем подключённым клиентам. При нескольких одновременных TUI-сессиях возможен backpressure и drop событий.

**Решение:** расширить протокол `subscribe` (уже частично описан в API.md §2.3): клиент указывает конкретные серверы, уровни логов, диапазон времени. Сервер фильтрует поток до отправки, снижая трафик. Добавить отдельный `multiplexer`-слой с per-connection буфером.

---

## 5. Опциональная CGO-сборка SQLite (приоритет: низкий)

**Проблема:** `modernc.org/sqlite` (pure-Go) заметно медленнее `mattn/go-sqlite3` (CGO) при высоком throughput истории.

**Решение:** build tag `sqlite_cgo` подключает `mattn/go-sqlite3` вместо `modernc`; default — по-прежнему pure-Go. Актуально для high-throughput инсталляций (R-7 в SRS.md §9.2).

---

## 6. Model aliasing / fallback-маппинг (приоритет: низкий)

**Проблема:** если клиент запрашивает модель, которой нет ни на одном healthy-сервере, прокси возвращает `ErrNoServer` / 503. Часть клиентов работает с целым семейством моделей (например, «любой 20B+ instruct») и не хочет получать 404, когда конкретное имя модели не задеплоено.

**Решение:** конфиг-параметр уровня `compat.model_aliases` (или отдельная секция) с правилами вида `from: <model> → to: [<candidate1>, <candidate2>, …]`. При получении запроса с моделью, которой нет ни на одном healthy-сервере, прокси подставляет первый доступный кандидат из списка и шлёт дальше; в логах и истории фиксируются оба имени (`requested_model` vs `actual_model`).

**Ограничение:** сейчас (базовая линия v0.9.3) при отсутствии модели возвращается `ErrNoServer` / 503 — это сознательный выбор до реализации aliasing'а.

## 7. Preflight-проверка shape `/v1/models` (приоритет: высокий)

**Проблема:** прокси нейтрален к бэкенду и принимает любой URL в `backends[].url`. Если пользователь по ошибке укажет non-OpenAI endpoint (Anthropic `/v1/messages`, Azure с `api-version`, native Ollama `/api/generate`), это всплывёт только на первом клиентском запросе как 404/500 без внятной диагностики.

**Решение:** на старте, после initial healthcheck, делать единичный `GET /v1/models` и валидировать shape ответа (`data: []` с объектами, имеющими `id: string`). Если shape не подходит — помечать сервер `unhealthy` и логировать WARN с указанием, что endpoint не OpenAI-совместим. Прокси продолжает работу — остальные сконфигурированные серверы остаются доступны.

**Риски:** один лишний HTTP-вызов на бэкенд при старте; пренебрежимый оверхед.

## 8. Retry с учётом 429, `Retry-After` и jitter (приоритет: высокий)

**Проблема:** текущая политика retry (FR-18..FR-20) не различает 5xx, сетевые ошибки и 429 rate-limit. Для cloud-бэкендов (OpenRouter, Groq, Together, OpenAI) это может усугублять rate limit'ы — failover на второй cloud-бэкенд только умножает шторм 429, вместо того чтобы переждать.

**Решение:**
- классифицировать upstream-ошибки: 4xx (кроме 429) → не ретраить; 429 / 503 → уважать `Retry-After` (секунды или HTTP-date), но не дольше `retry.max_backoff_ms`; 5xx / network → экспоненциальный backoff как сейчас;
- добавить jitter (например, `±20%`) к backoff-интервалам, чтобы избежать синхронных retry-волн;
- опциональный per-backend circuit breaker: после N подряд 429-х в окне — бэкенд помечается `unhealthy` на cool-down период.

**Риски:** небольшое изменение retry-семантики — существующие клиенты не должны регрессировать, потому что сейчас поведение «retry на любую ошибку», а новая политика строго менее агрессивна на 429.

## 9. Per-backend флаг `serialize_by_model` (приоритет: средний)

**Проблема:** model-affinity-маршрутизация (INV-2) сериализует запросы по модели на каждом сервере, чтобы не свопать VRAM. Для одно-модельных бэкендов (LM Studio, Ollama, vLLM, llama.cpp) это критично. Для много-модельных cloud-бэкендов (OpenRouter, Groq, Together — все модели доступны одновременно, swap'а VRAM нет) — чистый оверхед: запросы под разные модели, которые могли бы идти параллельно, выстраиваются в FIFO.

**Решение:** per-backend конфиг-флаг `serialize_by_model: auto | true | false` (default `auto`):
- `true` — сохранить текущее INV-2 поведение (single-model backend);
- `false` — отключить per-model сериализацию для этого бэкенда; запросы диспатчатся как только worker свободен, независимо от модели;
- `auto` — эвристика: если `/v1/models` отдал ≤ 2 моделей — `true`; если ≥ 10 — `false`; иначе лог-подсказка и default `true`.

**Риски:** усложняет worker loop планировщика; требует аккуратного тестового покрытия, чтобы single-model поведение не пострадало.

## 10. Теневой стриминг для хвоста генерации (приоритет: низкий/средний)

**Проблема:** фича «хвост генерации» (хоткей `t`, введена в v0.13.0) показывает последние сгенерированные токены только для запросов, которые **клиент** прислал в потоковом режиме (`"stream": true`). Если клиент шлёт `stream: false`, прокси идёт по non-streaming-пути (`runNonStream`): получает весь ответ от бэкенда одним куском в конце, промежуточных чанков нет — и в TUI выводится `non-streaming request — no live tail`. То есть наблюдаемость живой генерации зависит от поведения клиента, а не от возможностей бэкенда. Локальные серверы (LM Studio, Ollama, llama.cpp) стриминг поддерживают вне зависимости от того, как просит клиент.

**Решение:** опционально (флаг конфига, по умолчанию выкл.) для запросов, пришедших как non-streaming, прокси выполняет «теневой стриминг»: на бэкенд отправляет запрос с `stream: true`, по мере прихода SSE-чанков наполняет `core.LiveTail` (как в текущем streaming-пути), но **клиенту** возвращает единый собранный non-streaming JSON-ответ в конце — без потоковой передачи. Хвост при этом работает для любого запроса вне зависимости от поведения клиента.

**Риски/ограничения:**
- Поведенческое изменение пути ответа; должно быть строго opt-in через конфиг.
- Необходимо корректно реассемблировать полный ответ из дельт: накопление `content`, фрагментов `tool_calls` / `function_call`, агрегация `usage` (prompt/completion tokens), согласование `finish_reason` / `stop_reason`.
- Кросс-протокольная трансляция (OpenAI ↔ Anthropic) — учесть оба формата SSE.
- Отмена клиентом на середине стрима должна прерывать соединение с бэкендом без утечки горутин.
- Взаимодействие с INV-6: INV-6 запрещает ретрай/failover после отправки первого SSE-чанка клиенту. В теневом режиме клиенту чанки не уходят, поэтому ретрай и failover остаются разрешены вплоть до сборки финального ответа — это необходимо явно задокументировать и зафиксировать в реализации.
- Эмбеддинги не стримятся бэкендами и вне области применения.
