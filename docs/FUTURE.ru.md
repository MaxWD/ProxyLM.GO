## 1. Персистентность perf-статистики (приоритет: высокий)

**Проблема:** `PerfTracker` хранит все наблюдения `(server, model)` в RAM. При рестарте daemon'а история обнуляется; регрессия начинается заново с нуля — первые 2–3 запроса не дают метрик.

**Решение:** сохранять `[]perfObservation` в SQLite (новая таблица `perf_observations`), загружать при старте. Ограничить размер хранилища (например, 1000 наблюдений на пару, FIFO).

**Риски:** небольшой overhead на каждый завершённый запрос; нужна миграция 0003.

---

## 2. Ridge regression / регуляризация (приоритет: средний) — РЕАЛИЗОВАНО в v0.10.0

Реализовано как `(X^T X + λI)θ = X^T y` с λ = 1e-4 во всех 1/2/3-переменных солверах, плюс R² и 95% доверительные интервалы публикуются в `PerfStats` (`RSquared`, `TLoadCI`, `KInCI`, `KOutCI`, `FitQuality ∈ {"good","degraded",""}`). TUI подсвечивает degraded-строки в server-detail Info pane. См. `internal/core/perf.go`.

---

## 3. Per-endpoint статистика (приоритет: низкий) — РЕАЛИЗОВАНО в v0.10.0

Ключ регрессии теперь `(server, model, endpoint)`. Endpoint прокидывается из `RequestRecord.Endpoint` в `core.Job.Endpoint` → `Scheduler.recordPerf` → `PerfTracker.Record`. `ServerSummary` возвращает один `ModelSummary` на каждую пару `(model, endpoint)`; `ipc.ModelStats` получил новое поле `Endpoint`. В server-detail таблице TUI появилась колонка `Endpoint`.

## 4. Persistence in-memory очереди (приоритет: средний)

**Проблема:** при рестарте daemon'а все запросы из `pending` теряются — клиенты получают connection error и должны повторять сами. В production-инсталляциях это может вызывать значимые потери.

**Решение:** при старте с флагом `--durable-queue` сохранять `pending` в SQLite и восстанавливать при следующем старте. Запросы в статусе `running` при восстановлении переводятся в `queued` (повтор). Реализация требует гарантии идемпотентности на стороне клиента или явного флага `client_supports_retry`.

**Ограничение:** persistence очереди намеренно отложена до v0.2+ (U-3 в SRS.md).

---

## 5. Web UI (приоритет: низкий)

**Проблема:** TUI требует терминала; при удалённом мониторинге через браузер TUI неудобен.

**Решение:** минималистичный Web UI на том же WebSocket (`/admin/stream`), без зависимостей на фронтенде (vanilla JS + EventSource или WebSocket). Табличный вид запросов и шапка серверов — аналог TUI.

**Ограничение:** явно в out-of-scope MVP (SRS §8).

---

## 6. Аутентифицированный WS-мультиплекс с фильтрацией событий (приоритет: средний)

**Проблема:** текущий `/admin/stream` отдаёт все события всем подключённым клиентам. При нескольких одновременных TUI-сессиях возможен backpressure и drop событий.

**Решение:** расширить протокол `subscribe` (уже частично описан в API.md §2.3): клиент указывает конкретные серверы, уровни логов, диапазон времени. Сервер фильтрует поток до отправки, снижая трафик. Добавить отдельный `multiplexer`-слой с per-connection буфером.

## 7. Confidence interval и R² в server-detail modal (приоритет: низкий) — РЕАЛИЗОВАНО в v0.10.0

R² и half-width 95% CI вычисляются в `fillFitQuality` через σ̂² · diag((X^T X + λI)^-1) и публикуются как `t_load_ci`, `k_in_ci`, `k_out_ci` в `ModelStats`. В Info-pane сервера TUI колонки `↓tok/s` и `↑tok/s` отображаются как `38.5±5.1` при наличии CI; колонка `R²` показывает коэффициент; degraded-строки (R² < 0.70) подсвечиваются flash-стилем.

---

## 8. max_consecutive_requests_per_model — защита от голода (приоритет: средний) — РЕАЛИЗОВАНО в v0.10.0

Реализовано как **новая стратегия маршрутизации** `fair_share_round_robin` (вместо модификации существующих стратегий). При `scheduler.max_consecutive_per_model > 0` и достижении лимита `pool.PopForFairShare` принудительно берёт следующий FIFO-Job под другую модель. При отсутствии другой совместимой модели в очереди — fallback на обычный drain. См. `internal/core/pool.go`, `internal/core/scheduler.go` и раздел стратегий в `docs/ARCHITECTURE.ru.md`.

## 9. Опциональная CGO-сборка SQLite (приоритет: низкий)

**Проблема:** `modernc.org/sqlite` (pure-Go) заметно медленнее `mattn/go-sqlite3` (CGO) при высоком throughput истории.

**Решение:** build tag `sqlite_cgo` подключает `mattn/go-sqlite3` вместо `modernc`; default — по-прежнему pure-Go. Актуально для high-throughput инсталляций (R-7 в SRS.md §9.2).

---

## 10. Model aliasing / fallback-маппинг (приоритет: низкий)

**Проблема:** если клиент запрашивает модель, которой нет ни на одном healthy-сервере, прокси возвращает `ErrNoServer` / 503. Часть клиентов работает с целым семейством моделей (например, «любой 20B+ instruct») и не хочет получать 404, когда конкретное имя модели не задеплоено.

**Решение:** конфиг-параметр уровня `compat.model_aliases` (или отдельная секция) с правилами вида `from: <model> → to: [<candidate1>, <candidate2>, …]`. При получении запроса с моделью, которой нет ни на одном healthy-сервере, прокси подставляет первый доступный кандидат из списка и шлёт дальше; в логах и истории фиксируются оба имени (`requested_model` vs `actual_model`).

**Ограничение:** сейчас (базовая линия v0.9.3) при отсутствии модели возвращается `ErrNoServer` / 503 — это сознательный выбор до реализации aliasing'а.

## 11. Preflight-проверка shape `/v1/models` (приоритет: высокий)

**Проблема:** прокси нейтрален к бэкенду и принимает любой URL в `backends[].url`. Если пользователь по ошибке укажет non-OpenAI endpoint (Anthropic `/v1/messages`, Azure с `api-version`, native Ollama `/api/generate`), это всплывёт только на первом клиентском запросе как 404/500 без внятной диагностики.

**Решение:** на старте, после initial healthcheck, делать единичный `GET /v1/models` и валидировать shape ответа (`data: []` с объектами, имеющими `id: string`). Если shape не подходит — помечать сервер `unhealthy` и логировать WARN с указанием, что endpoint не OpenAI-совместим. Прокси продолжает работу — остальные сконфигурированные серверы остаются доступны.

**Риски:** один лишний HTTP-вызов на бэкенд при старте; пренебрежимый оверхед.

## 12. 429-aware retry с `Retry-After` и jitter (приоритет: высокий)

**Проблема:** retry-политика (FR-18..FR-20) не различает 5xx, network errors и 429 rate-limit. Для cloud-бэкендов (OpenRouter, Groq, Together, OpenAI) это может усиливать rate-limit — failover на второй cloud-бэкенд умножает 429 вместо того, чтобы выждать паузу.

**Решение:**
- классифицировать upstream-ошибки: 4xx (кроме 429) → без retry; 429 / 503 → уважать `Retry-After` (секунды или HTTP-date), с верхней границей `retry.max_backoff_ms`; 5xx / network → экспоненциальный backoff как сейчас;
- добавить jitter (например, `±20%`) к интервалам backoff, чтобы избежать синхронных волн retry;
- опционально per-backend circuit breaker: после N последовательных 429 в окне — считать бэкенд `unhealthy` на cool-down период.

**Риски:** небольшое изменение retry-семантики — клиентов не должно сломать, потому что сейчас политика «retry на любую ошибку», а новая строго менее агрессивна на 429.

## 13. Per-backend флаг `serialize_by_model` (приоритет: средний)

**Проблема:** model-affinity routing (INV-2) сериализует запросы по модели на одном сервере, чтобы избежать VRAM-swap'ов. Для одно-модельных бэкендов (LM Studio, Ollama, vLLM, llama.cpp) это критично. Для multi-model cloud-бэкендов (OpenRouter, Groq, Together — все модели доступны одновременно, нет VRAM-swap'а) — это чистый оверхед: запросы для разных моделей, которые могли бы идти параллельно, ставятся в очередь последовательно.

**Решение:** per-backend параметр `serialize_by_model: auto | true | false` (default `auto`):
- `true` — нынешнее поведение INV-2 (одно-модельный бэкенд);
- `false` — отключить per-model сериализацию; запросы уходят как только worker свободен, независимо от модели;
- `auto` — эвристика: если `/v1/models` возвращает ≤ 2 моделей — `true`; если ≥ 10 — `false`; иначе лог-подсказка и `true` по умолчанию.

**Риски:** усложняет worker-loop планировщика; нужно покрытие тестами, чтобы одно-модельное поведение не пострадало.
